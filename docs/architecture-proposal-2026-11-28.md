# Предложение: структура проекта, в которой казусы видны сразу

Статус: **предложение** (proposed), не утверждено. Ревизия: `ae2e70e` + ветка `claude/game-bug-hunt-tux8nw`. Основание — поиск багов 2026-11-28 ([отчёт](bug-hunt-2026-11-28.md)). Каждый этап ниже начинается только после отдельного «да» владельца; по CLAUDE.md переименования, сжатие правок и перестройка архитектуры требуют отдельного одобрения.

## 1. Зачем

Цель — чтобы ИИ-помощник (и человек) тратил время на улучшение игры, а не на восстановление того, что в игре реально работает. Сейчас почти любая задача начинается с ручной сборки итогового кода из десятков патчей, а большая часть найденных багов — расхождения между местами, где одно и то же записано дважды.

## 2. Как устроено сейчас (факты на `ae2e70e`)

| Что | Факт | К чему приводит |
|---|---|---|

Правка = «найди этот кусок текста ровно один раз и замени». Порядок задаётся именем файла (`script-05.zzzzzzzzzzzzzzzzzzzz-warrior-talents`). | Чтобы понять поведение, нужно собрать итоговый код. ## 3. Целевая структура

```text
src/
  data/                      ← всё, что описывает игру, без логики
    classes/<class>.json     ← классы, спеки, роли, базовые статы, автоатака (с флагом ranged)
    abilities/<class>.json   ← умения: имя, иконка, спек, уровень, цена, перезарядка, эффекты, приоритет ИИ
    effects.json             ← типы эффектов: как называются, как показываются (значок, пассивка, без счётчика)
    passives/<class>.json    ← пассивки и их уровни (15/30), инструменты классов, обереги
    pets.json, enemies/, quests/, items/, talents/<class>.json (уже есть)
    rules/                   ← таблицы из документов в машинном виде (график питомцев, уровни тренера)
  engine/                    ← логика боя, без текстов и чисел умений
    battle.js  effects.js  ai.js  progression.js  xp.js  dungeon.js
  ui/                        ← экраны: hero.js, gear.js, talents.js, battle-view.js, map.js …
  assets/                    ← картинки и звук только файлами; встраиваются при сборке
scripts/
  build.py                   ← одна сборка, её же используют тесты
  tests/                     ← правила, карточки, браузерные сценарии
```

### 3.1 Одно описание умения

```json
"fireblast": {
  "name": "Огненный взрыв", "icon": "spell_fire_fireball", "spec": "fire", "unlock": 1,
  "cost": {"mana": 7}, "cd": 3,
  "effects": [{"type": "damage", "mult": 1.6, "school": "fire", "target": "enemy"}],
  "ai": {"priority": 2}
}
```

Из этой записи выводятся:

- **текст** для игрока — собирается из `effects` по шаблону («160% урона огнём»), поэтому не может разойтись с числом;
- **действие в бою** — общий исполнитель эффектов вместо отдельной ветки `if` на каждое умение;
- уровень в «Герое», превью класса, окне талантов, карточках и тестах.

Особые умения (Ни шагу назад, Soul Link) остаются кодом, но тоже объявляются в данных с типом `custom` и обязательным описанием.

### 3.2 Эффекты с обязательным показом

Каждый тип эффекта в `effects.json` указывает: название, иконку, где показывать (бой, «Герой», оба), и `permanent: true` для эффектов на весь бой (без счётчика). Эффект без описания — ошибка проверки данных при сборке, а не баг, который находит игрок.

### 3.3 ИИ как приоритеты, а не как ветки

ИИ спека — упорядоченный список правил «условие → умение» (`"if": "hp<0.65 && !has(reflect)"`). Тогда видно, почему умение не применяется, а тест «каждое умение когда-нибудь применяется» сразу указывает на правило, которое его блокирует.

## 4. Проверки, которые ловят казусы

| Проверка | Что ловит | Статус |
|---|---|---|
| Правила классов (`test_class_rules.cjs`) | Неприменяемые умения, расхождение уровней, эффекты на весь бой, посох у кастера, пассивки раньше срока, длительность оглушений, служебные тексты, ростер питомцев | **Сделано** (шаг 1), 158 известных нарушений с номерами находок |
| Карточки классов (`report_class_cards.cjs`) | Всё вышеперечисленное глазами владельца на одной странице | **Сделано** (шаг 1) |
| Проверка данных при сборке | Умение без текста/иконки/уровня, эффект без описания, ссылка на несуществующее умение | После этапа B |
| Тексты из данных + проверка «число в тексте = число в эффекте» | «На 2 хода» при одном, «+15%» при +10% | После этапа C |
| Браузерный сценарий «новый игрок» | Пустое сохранение → создать героя каждого класса → первый бой → «Герой», экипировка, таланты на трёх размерах экрана: скриншоты в альбом, белые страницы без стилей, нечитаемый контраст, ошибки консоли, запросы к внешним сайтам | Этап A (можно сразу) |
| Запрет внешних адресов в сборке | Иконки с `wow.zamimg.com`, которые не грузятся без сети | Этап A |

## 5. План перехода

Каждый этап — отдельная ветка и PR, игра после каждого этапа ведёт себя так же (кроме этапов, где явно чиним баги).

**A. Защитная сетка (1–2 сессии).** Браузерный сценарий «новый игрок», запрет внешних адресов, отпечаток боя: для набора сидов сохранить события боя и сравнивать байт в байт. Это даёт доказательство «поведение не изменилось» для этапа B.

**B. Свернуть правки в обычные модули (2–4 сессии).** Один раз собрать итоговый код и сделать его исходником, разбитым на модули по системам (`engine/*`, `ui/*`). Картинки вынести в `assets/`. Одна сборка для игры и тестов. Гейт: отпечаток боя совпадает байт в байт, все тесты зелёные, старые сохранения грузятся (резервная копия, синтетические сохранения). После этого правки `.edits.json` больше не создаются. Это продолжение ARCH-01 (`src/core/` уже начат).

**C. Данные умений (по классу за раз, 1 сессия на класс).** Перенести умения класса в `data/abilities/<class>.json`, тексты генерировать. Начинать с класса, у которого больше всего багов (паладин или разбойник), заодно с TALENT-03 — наборы всё равно переписываются. Гейт: тест правил без новых нарушений, карточка класса прочитана владельцем.

**D. Эффекты и ИИ как данные.** После C для всех классов.

### Что не трогаем без отдельного решения

Ключи сохранений и идентификаторы (`azeroth-ab-setup-v5`, `azeroth-arms-hero-v1`, id умений), утверждённые арт и звук, баланс (кроме исправления явных багов), процесс публикации из `main`.

### Риски

- Этап B меняет почти все файлы — его PR большой. Снижение риска: отпечаток боя и полный прогон тестов, отдельная проверка сохранений, без изменения поведения в этом же PR.
- Пока идёт переход, параллельная работа в старых правках создаёт конфликты. Лучше на время этапа B не вносить игровых изменений.
- Генерация текстов (этап C) поменяет формулировки, которые владелец уже читал. Шаблоны текстов утверждает владелец.

## 6. Что это даст

- Новое умение — одна запись в данных; тесты сразу говорят, если текст, уровень или ИИ не сходятся.
- ИИ-помощник читает конкретный модуль вместо сборки 137 файлов: меньше токенов на разбор, меньше ошибок «правил не там».
- Владелец смотрит карточки классов и альбом скриншотов вместо прохождения каждого класса.
